## 0. Зафиксированные решения

| Вопрос | Решение | Почему |
|---|---|---|
| Кто считает правила | **Сервер.** Движок `domain` выносится в KMP-модуль `:rules` и компилируется в JS для serverless-функции | Один исходник правил на клиенте и сервере; клиент не может подделать ход и не получает карт соперника |
| Транспорт обновлений | **Supabase Realtime** (WebSocket) на чтение, HTTP на запись | Мгновенные ходы; клиент не пишет в базу напрямую — иначе серверный авторитет теряет смысл |
| Платформы v1 | **Web (TeaVM) + Desktop (LWJGL3)** | Desktop нужен ещё и как средство отладки: два окна на одной машине |
| Идентификация | **Supabase anonymous auth + ник** | Настоящий JWT без регистрации, работают RLS-политики, сессия переживает F5 |
| Тайм-аут | **Таймер хода + автосдача** | Партии не висят вечно; см. §9 — Vercel Hobby не даёт минутного cron, поэтому просрочка снимается «лениво» |
| Поиск комнаты | **Общий список открытых комнат + вход по коду** | Код нужен, чтобы позвать конкретного человека, не листая список |
| Объём v1 | Базовая сетевая партия + **реконнект в свою партию** | Реванш, чат, зрители и рейтинг — вне первой версии |
| Хостинг | Vercel (функции + статика игры) и Supabase (Postgres, Auth, Realtime), оба на бесплатном тарифе | Ограничения тарифов учтены в §12 |

Одиночная игра против ИИ не меняется ни по правилам, ни по коду экрана: сетевая партия — второй источник тех же `GameEvent`.

## 1. Что должно получиться

Сценарий целиком:

1. Игрок запускает игру → в главном меню появляется пункт **«Игра по сети»**.
2. Первый вход: анонимная авторизация в Supabase, игрок вводит ник (хранится локально и в профиле).
3. Экран списка комнат: открытые комнаты (название, ник хозяина, значок замка, время создания), кнопки «Создать», «Обновить», поле «Войти по коду».
4. Создание комнаты: название, необязательный пароль → игрок попадает в лобби комнаты и ждёт соперника. У комнаты есть код из 6 символов.
5. Второй игрок жмёт на комнату (при пароле — вводит его) → сервер сажает его на второе место и **сразу стартует партию**: бросок кубиков, раздача, первый ход.
6. Партия идёт на том же `GameScreen`, что и против ИИ. Ход отправляется на сервер, ответ приходит по Realtime, события проигрываются анимацией. Виден таймер хода и ник соперника.
7. Просрочка таймера — победа соперника. Кнопка «Сдаться» — то же самое, но добровольно.
8. F5, потеря связи, перезапуск игры → при входе в сетевой раздел игрок автоматически возвращается в свою активную партию с актуальным состоянием.

## 2. Ограничения, из которых выросла архитектура

1. **Vercel не исполняет JVM.** Доступны Node.js и Edge (Deno у Supabase Functions). Значит серверная сторона — JavaScript, и движок должен существовать в виде JS.
2. **Веб-клиент собирается TeaVM.** Ktor, `supabase-kt`, OkHttp и всё, что тянет корутины с диспетчерами и рефлексию, там не работают. Сетевой слой пишем сами поверх минимума: `Gdx.net` для HTTP, платформенный WebSocket.
3. **`GameState` содержит обе руки и обе колоды.** Отдать его клиенту целиком — значит отдать карты соперника. Нужен слой редактирования состояния и событий (§6).
4. **Домен уже чистый.** `gdx/core/src/main/kotlin/com/first/game/domain/` не импортирует `com.badlogic.*` — вынос в KMP-модуль механический, без переписывания правил.
5. **Движок уже подходит для PvP.** `GameEngine.apply` останавливается на `AWAITING_PLAY`/`AWAITING_CHOICE` нужной стороны и сам ИИ не дёргает — тот вызывается из `GameScreen`. В сетевой партии его просто не вызывают.

### 3.1 KMP-модуль

```kotlin
// gdx/rules/build.gradle.kts
plugins { kotlin("multiplatform") }

kotlin {
    jvm { compilations.all { kotlinOptions.jvmTarget = "17" } }
    js(IR) {
        nodejs()
        binaries.library()        // артефакт кладётся в server/lib
        generateTypeScriptDefinitions()
    }
    sourceSets {
        commonTest.dependencies { implementation(kotlin("test")) }
    }
}
```

Грабли, которые ждут на этом шаге:

- **TeaVM ест JVM-байткод**, то есть `rules-jvm`. В домене нет ничего, кроме `kotlin.random.Random` и коллекций, — риск низкий, но собрать веб-сборку надо сразу после переезда, до всей остальной работы.
- **Тесты**: сейчас это JUnit 5 (`useJUnitPlatform`). В `commonTest` доступен только `kotlin.test`. Проще всего перенести файлы в `commonTest` на `kotlin.test`-ассёрты, оставив запуск на JVM-таргете; тесты ИИ и инвариантов при этом остаются такими же.
- **`@JsExport` живёт только в js-таргете** — фасад пишется в `jsMain` и вызывает общий код.

### 3.2 Формат состояния

Кодек — один на всех: сервер хранит состояние строкой, клиент разбирает её тем же кодом, рассинхрон форматов невозможен по построению.

За основу берётся уже работающий формат `SaveGame.encode/decode` (`gdx/core/src/main/kotlin/com/first/game/SaveGame.kt`): плоские строки, разделители `\n`, `;`, `,`, номер версии первой строкой. Он переезжает в `rules/commonMain/.../net/StateCodec.kt` и расширяется полем `outcome`; `SaveGame` начинает пользоваться им и перестаёт держать собственную копию разбора.

**Почему не kotlinx.serialization:** её пришлось бы протаскивать в TeaVM-сборку, а это лишний риск ради состояния, которое умещается в семь строк текста. JSON нужен только на границе HTTP — там его собирает и разбирает серверная сторона (TypeScript) и минимальный клиентский парсер ответов API.

### 3.3 Фасад для сервера

```kotlin
// jsMain — как реализовано
@JsExport object MatchFacade {
    fun newMatch(seed: String): JsMatchResult
    fun apply(state: String, seat: String, command: String, seed: String): JsMatchResult
    fun viewFor(state: String, seat: String): String?      // состояние места, без чужих карт
    fun eventsFor(events: String, seat: String): String?   // события места, без чужих карт
    fun isOver(state: String): Boolean
    fun winnerSeat(state: String): String?                 // "A" | "B" | null
    fun actingSeat(state: String): String?                 // чьей команды ждут
}

@JsExport class JsMatchResult(val ok: Boolean, val error: String?, val state: String, val events: String)
```

Ошибки возвращаются кодом (`NOT_YOUR_TURN`, `ILLEGAL_COMMAND`, `MATCH_FINISHED`, `BAD_STATE`, `BAD_COMMAND`, `BAD_SEAT`), а не исключением: серверной функции проще превратить код в HTTP-ответ, чем ловить исключение через границу языков. Логика живёт в `MatchService` из общего кода — фасад только переводит типы, поэтому и тестируется на обеих платформах.

Невозможную команду движок отбивает молча: возвращает прежнее состояние и пустой список событий (`GameEngine.kt`). Отсюда критерий `ILLEGAL_COMMAND` — событий нет, значит показывать нечего и ход не состоялся.

Серверная функция не знает правил вообще: она проверяет права и очерёдность, зовёт `apply`, сохраняет результат и раскладывает по двум видам.

## 4. Места, стороны и перспектива

Домен оперирует `Side.YOU` и `Side.AI` — переименовывать их незачем, это сломало бы половину презентации ради косметики. Вводится соглашение:

| Место в комнате | Сторона в `GameState` |
|---|---|
| `A` — хозяин комнаты | `Side.YOU` |
| `B` — гость | `Side.AI` |

Сервер хранит состояние в «системе координат места A». Клиенту места B состояние и события отражаются функцией `Mirror.flip(...)`: меняются местами `you`/`ai`, `forbidOnYou`/`forbidOnAi`, `trapsOnYou`/`trapsOnAi`, переворачиваются `turn`, `firstPlayer`, `pending.side`, `outcome.winner` и `side` у каждого события.

Итог: **каждый клиент видит себя как `Side.YOU`**, и `GameScreen` не догадывается, что играет по сети. Инвариант проверяется тестом `flip(flip(state)) == state`.

## 5. Что клиент отправляет и получает

Клиент отправляет ровно те же `Command`, что и в одиночной игре: `PlayCard(handIndex)`, `ChooseOption(optionIndex)`. Индексы — по **своему** редактированному виду, который для собственной стороны совпадает с настоящим состоянием, поэтому пересчёт не нужен.

Плюс два внеигровых действия: `Surrender` и `ClaimTimeout` (см. §9) — они не команды движка, а отдельные endpoint'ы.

## 6. Скрытая информация

Что нужно спрятать от соперника:

| Данные | Кому видно | Комментарий |
|---|---|---|
| Своя рука | только владельцу | главное, что защищаем |
| Порядок колоды | **никому, включая владельца** | знать свою колоду — значит знать будущее; решено при реализации, строже первоначального плана |
| Варианты чужого выбора | никому | по ловушке они строятся прямо из руки, см. ниже |
| Размер руки и колоды | обоим | HUD их показывает |
| SPACE, DISCARD | обоим | лежат в открытую и сейчас |
| Запреты, ловушки, чей ход, счёт | обоим | — |

**Найдено при реализации:** `ChoiceKind.TRAP_DISCARD` строит варианты сброса прямо из руки (`GameEngine.kt`, `hand.mapIndexed`). Такой `PendingChoice` — и в состоянии, и в событии `ChoiceRequired` — раскрыл бы руку соперника карта за картой. Поэтому у чужого выбора вырезаются варианты целиком, независимо от вида выбора: сам факт «соперник думает» остаётся, содержимое нет.

Хорошая новость: **презентация уже не показывает лица чужих карт.** В `GameScreen.animate` события добора отрисовываются как `letter = event.letter.takeIf { event.side == Side.YOU }`, а рука соперника раскладывается рубашками (`CardActor(assets, null, faceUp = false)`). Значит достаточно вырезать данные на сервере, экран к этому уже готов.

**`Redact.state(state, viewer)`**: скрытые стопки заменяются списками той же длины из карт-заглушек (`Letter.F`), `space` и `discard` остаются, у чужого `pending` вырезаются варианты.

**`Redact.events(events, viewer)`**: у чужих `CardDealt` и `CardDrawn` буква заменяется заглушкой, у чужого `ChoiceRequired` — варианты. `TrapTriggered`, `HandOverflow`, `CardForbidden`, `CardStolen`, `CardRecovered` не редактируются — все они кладут карту в открытый сброс или берут из него, эту информацию соперник и так видит.

Флага `redacted` в самом состоянии нет: доменный тип не должен обрастать сетевыми полями. Факт редактирования сообщает API-ответ, а не строка состояния.

**Задача на реализацию (обязательная):** аудит презентации на чтение чужих букв. Прогнать `GameScreen`, `AnimationDirector` и HUD и убедиться, что ни одна ветка не смотрит в `state.ai.hand`/`state.ai.deck` иначе как за размером. В сетевом режиме туда попадают заглушки, и любое чтение буквы даст ложный показ.

## 7. Схема базы

```sql
-- профиль поверх анонимного пользователя
create table profiles (
  id          uuid primary key references auth.users(id) on delete cascade,
  nickname    text not null check (char_length(nickname) between 2 and 16),
  created_at  timestamptz not null default now()
);

create type room_status as enum ('lobby', 'playing', 'closed');

create table rooms (
  id             uuid primary key default gen_random_uuid(),
  code           text not null unique,              -- 6 символов, без похожих (0/O, 1/I)
  name           text not null check (char_length(name) between 1 and 24),
  host_id        uuid not null references profiles(id),
  guest_id       uuid references profiles(id),
  password_hash  text,                              -- bcrypt; null = без пароля
  status         room_status not null default 'lobby',
  match_id       uuid,
  created_at     timestamptz not null default now(),
  last_activity  timestamptz not null default now()
);

create table matches (
  id             uuid primary key default gen_random_uuid(),
  room_id        uuid not null references rooms(id) on delete cascade,
  seat_a         uuid not null references profiles(id),
  seat_b         uuid not null references profiles(id),
  state          text not null,                     -- StateCodec, координаты места A
  seed           text not null,                     -- база детерминизма, см. §8
  version        int  not null default 0,           -- растёт на каждую применённую команду
  turn_deadline  timestamptz not null,
  status         text not null default 'playing',   -- playing | finished
  winner_seat    char(1),                           -- 'A' | 'B'
  end_reason     text,                              -- FIRST_SET | FIVE_OF_A_KIND | DECK_OUT | TIMEOUT | SURRENDER
  created_at     timestamptz not null default now(),
  updated_at     timestamptz not null default now()
);

-- то, что реально видит клиент; ровно две строки на партию
create table match_views (
  match_id    uuid not null references matches(id) on delete cascade,
  player_id   uuid not null references profiles(id),
  seat        char(1) not null,
  version     int  not null,
  state       text not null,                        -- редактированное, в своей перспективе
  events      text not null default '',             -- события последнего применения
  deadline    timestamptz not null,
  updated_at  timestamptz not null default now(),
  primary key (match_id, player_id)
);

create index on rooms (status, last_activity desc);
create index on matches (status, turn_deadline);
```

### 7.1 RLS

Все таблицы — `enable row level security`. Пишет только сервер, поэтому политик `insert`/`update`/`delete` нет **ни одной**: serverless-функция ходит с `service_role`-ключом и RLS обходит.

```sql
-- профиль: свой читаем и заводим сами (это единственная клиентская запись)
create policy p_self  on profiles     for select using (id = auth.uid());
create policy p_ins   on profiles     for insert with check (id = auth.uid());

-- вид партии: только свой
create policy mv_self on match_views  for select using (player_id = auth.uid());

-- matches и rooms клиент напрямую не читает вовсе:
-- в matches лежит полное состояние, в rooms — хеш пароля.
```

Список комнат и ники соперников отдаёт **функция API**, а не прямой select — так `password_hash` физически не может утечь (RLS фильтрует строки, но не колонки).

### 7.2 Realtime

```sql
alter publication supabase_realtime add table match_views;
```

Миграции применяются через пул, а не через `db.<ref>.supabase.co`: прямое подключение у новых проектов работает только по IPv6, и `supabase db push` без строки пула падает с `tls error (EOF)`. Рабочая команда — в [server/README.md](../../server/README.md).

Клиент подписывается на `postgres_changes`, событие `*`, схема `public`, таблица `match_views`, фильтр `player_id=eq.<uid>`.

**Проверено на живом проекте** (`server/checks/realtime-smoke.mjs`): подписка **без** фильтра тоже принимается, но чужие строки по ней не приходят — RLS применяется к Realtime, и защищает именно она, а фильтр лишь сокращает трафик. Кадр `phx_join` должен нести `access_token` с JWT игрока: под анонимной ролью политика `authenticated` не срабатывает и не приходит ничего. Без heartbeat раз в ~25 секунд соединение закрывается.

`rooms` в публикацию **не** добавляем: список комнат обновляется по кнопке и раз в 5 секунд, пока открыт экран списка. Живая подписка на лобби — цена без пользы; исключение — экран ожидания соперника, где хозяину нужен мгновенный старт (см. §8, шаг 5): он опрашивает `GET /api/rooms/{id}` раз в 2 секунды, пока ждёт.

## 8. API

Всё на Vercel, Node runtime (не Edge — нужен `service_role`-ключ и bcrypt). Общее для всех запросов:

- заголовок `Authorization: Bearer <supabase JWT>`, функция валидирует его через Supabase Auth **(проверить формат проверки: локально по JWT-секрету проекта или запросом `GET /auth/v1/user`)**;
- CORS: `Access-Control-Allow-Origin` — домен игры и `http://localhost:*` для отладки;
- ответы — JSON; ошибки `{ "error": "<code>" }` с кодами из §8.1.

| Метод | Путь | Тело | Что делает |
|---|---|---|---|
| POST | `/api/profile` | `{nickname}` | Создаёт или переименовывает профиль |
| GET | `/api/rooms` | — | Список комнат в статусе `lobby`: `id, code, name, hostNickname, hasPassword, createdAt`. Пароль и его хеш не отдаются никогда |
| POST | `/api/rooms` | `{name, password?}` | Создаёт комнату. Один игрок — одна открытая комната: прежняя закрывается |
| GET | `/api/rooms/{id}` | — | Состояние комнаты для ожидающего хозяина: статус, ник гостя, `matchId` |
| POST | `/api/rooms/join` | `{roomId?, code?, password?}` | Сажает на место B и стартует партию. Возвращает `{matchId, seat}` |
| POST | `/api/rooms/{id}/leave` | — | Выход из лобби; если ушёл хозяин — комната закрывается |
| POST | `/api/matches/{id}/command` | `{version, kind: "play"\|"choose", index}` | Главный endpoint: применяет команду |
| POST | `/api/matches/{id}/surrender` | — | Сдаться |
| POST | `/api/matches/{id}/claim-timeout` | — | Просит засчитать просрочку соперника |
| GET | `/api/matches/current` | — | Реконнект: активная партия игрока и её вид |
| GET | `/api/cron/reap` | — | Уборка: закрытие протухших комнат и просроченных партий |

### 8.1 Коды ошибок

`unauthorized`, `nickname_required`, `room_not_found`, `room_full`, `wrong_password`, `already_in_room`, `match_not_found`, `not_your_match`, `not_your_turn`, `stale_version`, `illegal_command`, `match_finished`.

### 8.2 Обработка команды — по шагам

```
1. Проверить JWT → playerId.
2. Прочитать matches по id. Нет — match_not_found.
3. Определить место игрока (seat_a/seat_b). Не участник — not_your_match.
4. status = finished → match_finished.
5. now > turn_deadline → завершить партию по тайм-ауту (§9) и вернуть текущее состояние.
6. version из тела ≠ matches.version → stale_version (клиент отстал; он подтянет вид и повторит).
7. MatchFacade.apply(state, seat, command, seed#version).
   ERR → illegal_command (это либо баг клиента, либо попытка сжульничать: логировать).
8. Одной транзакцией:
     matches: state, version+1, turn_deadline = now + TURN_SECONDS, updated_at
              (при isOver: status=finished, winner_seat, end_reason)
     match_views: по строке на место — redact + mirror(для B), events, version, deadline
     rooms.last_activity = now (при isOver: status=closed)
9. Ответ: свой вид (тот же, что придёт по Realtime).
```

Пункт 9 не лишний: он делает клиент работоспособным даже при неподнявшемся WebSocket — свой ход виден всегда, ждать по сети приходится только чужой.

**Очерёдность** отдельно не проверяется: движок сам вернёт ошибку, если команду прислало не то место. Дополнительно `apply` получает `seat` и обязан отклонить команду, чей `actingSide` не соответствует месту, — это единственная защита от «хожу за соперника».

### 8.3 Детерминизм

`kotlin.random.Random` не отдаёт своё состояние наружу, а состояние партии хранится строкой между вызовами функции. Поэтому RNG воссоздаётся при каждом применении: `SeededRng(hash(match.seed, match.version))`. Партия воспроизводима по паре «seed + журнал команд», а серия команд не может дать один и тот же бросок дважды.

## 9. Таймер хода, разрывы, уборка

`TURN_SECONDS = 60` (константа сервера; клиент получает `deadline` и рисует обратный отсчёт).

Просрочка снимается тремя путями, потому что **Vercel Hobby не даёт минутный cron — только один запуск в сутки (проверить актуальные лимиты тарифа)**:

1. **Лениво**: любой запрос к матчу первым делом проверяет `turn_deadline`.
2. **По требованию соперника**: клиент, видящий, что таймер истёк, шлёт `claim-timeout`; сервер сверяет со своими часами и завершает партию. Это основной путь — заинтересованная сторона в этот момент онлайн.
3. **Cron раз в сутки** `/api/cron/reap`: закрывает комнаты в `lobby` старше часа и партии, где `turn_deadline` старше суток. Мусор, а не механика.

Обрыв связи от долгого раздумья не отличается: часы идут в обоих случаях. Отдельного состояния «пауза» в v1 нет.

**Реконнект**: при входе в сетевой раздел клиент зовёт `GET /api/matches/current`. Есть партия — сразу открывается `GameScreen` с полученным состоянием, без раздачи и без анимаций (как `continueGame` для отложенной партии, только состояние приходит с сервера). Нет — открывается список комнат.

### 10.1 Пакет `core/net`

```
core/src/main/kotlin/com/first/game/net/
├── Auth.kt          # анонимный вход, refresh, хранение токенов в GamePrefs

```

- **HTTP** — `Gdx.net.sendHttpRequest`: работает и в TeaVM (через XHR), и на десктопе. Одна реализация на обе платформы.
- **WebSocket** — платформенная: на десктопе `java.net.http.WebSocket` (есть в JDK 17, зависимостей не нужно), в вебе `org.teavm.jso.websocket.WebSocket`. Реализация передаётся в игру из лаунчера (`Lwjgl3Launcher`, `TeaVMLauncher`), `core` знает только интерфейс.

- **Деградация**: если сокет не поднялся за 5 секунд или отвалился, клиент переходит на опрос `GET /api/matches/current` раз в 2 секунды и продолжает пытаться подключиться. Игра остаётся играбельной, просто с задержкой.

Все ответы приходят в игровой поток через очередь: `Gdx.app.postRunnable` — трогать сцену из сетевого колбэка нельзя.

### 10.2 Авторизация

Анонимный вход даёт `access_token` (короткий) и `refresh_token` (долгий). Оба лежат в `GamePrefs` (в вебе это localStorage), при старте токен обновляется через `POST /auth/v1/token?grant_type=refresh_token`. Ник спрашивается один раз и уходит в `POST /api/profile`.

**Проверено на живом проекте:** анонимный вход — это `POST /auth/v1/signup` с пустым телом `{}` и заголовком `apikey`. В ответ приходят `access_token` (час), `refresh_token` и `user.is_anonymous = true`. В настройках проекта опция включается полем `external_anonymous_users_enabled`.

Ключи у проекта двух поколений: старые JWT (`anon`, `service_role`) и новые (`sb_publishable_…`, `sb_secret_…`). Берём новые: публикуемый — в игру, секретный — только в переменные окружения сервера.

## 11. Безопасность

| Угроза | Ответ |
|---|---|
| Клиент подделывает ход | Правила считает сервер; клиент шлёт только `handIndex`/`optionIndex` |
| Клиент ходит за соперника | `apply` сверяет место с `actingSide` |
| Клиент читает карты соперника | В `match_views` лежит редактированное состояние; полное — только в `matches`, куда RLS не пускает никого |
| Подбор пароля комнаты | bcrypt-хеш; на неудачные попытки — счётчик на комнату, после 10 за 10 минут вход отклоняется |
| Утечка `service_role`-ключа | Только в переменных окружения Vercel. Никогда не попадает в клиент; проверить, что его нет в `teavm/build/dist` |
| Повтор запроса (двойной тап) | `version` в теле команды: второй запрос получит `stale_version` |
| Мусорные комнаты | Одна открытая комната на игрока + уборка по `last_activity` |
| Оскорбительные ники | В v1 — только ограничение длины и набора символов. Модерации нет |

Факт: развёрнуто на `https://first-game-api.vercel.app`. Проверка `server/checks/api-smoke.mjs` играет партию целиком через HTTP (по умолчанию поднимая функцию локально, с `API_BASE` — против деплоя) и проверяет отказы: чужой ход, старая версия, посторонний в партии, ход в законченную партию, неверный пароль, занятая комната, отсутствующий и поддельный токен, тайм-аут.

Отклонения от плана, принятые при реализации:

- **Одна функция вместо файла на маршрут.** Бесплатный тариф даёт двенадцать функций на проект, а эндпоинтов больше; `vercel.json` переписывает `/api/*` на `api/index.js`, внутри свой роутер. Побочно: холодный старт один на всё API.
- **JavaScript, а не TypeScript.** Шага сборки нет вовсе: функция подключает готовый `lib/rules/first-game-rules.js` напрямую. Библиотека Kotlin/JS — CommonJS, поэтому в её каталоге лежит свой `package.json` с `"type": "commonjs"`, иначе Node читает UMD-обёртку как ES-модуль и падает.
- **Собранные правила коммитятся** в `server/lib/rules/` (~224 КБ): Vercel деплоит содержимое репозитория, а JVM и Gradle там нет. Обновляются `server/scripts/sync-rules.sh`.
- **Колонка `matches.acting_seat`.** Тайм-аут считает база, а чей ход — записано внутри строки состояния, которую разбирает только движок. Сервер проставляет место после каждого хода, и тогда `expire_matches` может сама определить победителя.
- **Вход в комнату и тайм-аут — функции базы** (`join_room`, `expire_matches`, миграция `20260809073000`). И то и другое гонка: двое жмут на одну комнату одновременно, двое клиентов одновременно замечают просрочку. Пароль сверяется там же через pgcrypto и не покидает базу.
- **Оптимистическая блокировка на версии.** Ход сохраняется запросом `version=eq.<ожидаемая>`; не нашлось строки — значит кто-то опередил, и клиент получает `stale_version`. Это же гасит двойной тап.
- **Токен проверяется запросом к Supabase** (`/auth/v1/user`), а не разбором JWT на месте: новые ключи проекта подписаны асимметрично, и локальная проверка потребовала бы JWKS с ротацией. Ответы кэшируются на минуту в экземпляре функции.

Прогон `./gradlew lwjgl3:run -Pfirst.net=duel` играет партию через настоящий сервер (второй игрок изображается голыми запросами), `-Pfirst.net=poll` делает то же без сокета. Оба доигрывают до победы.

Два дефекта, найденных прогоном и исправленных:

- **Клиент замирал навсегда**, если во время ожидания ответа на свой ход по сокету приходил новый вид: команда отбрасывалась (защита от двойного тапа), а повторного сигнала уже не было. Теперь после ответа клиент повторяет последний вид без событий — состояние актуально, играть заново нечего.
- **`/matches/current` отдавал только активные партии**, поэтому игрок без сокета не узнавал исход: его последний ход был чужим, а спросить негде. Теперь законченная партия отдаётся ещё десять минут — заодно это и есть экран результата при возврате.

JSON разбирается через `JsonReader` libGDX (без рефлексии, поэтому одинаково работает в вебе), тела запросов собираются строкой. Время до просрочки считается своим разбором ISO-8601: `java.time` в веб-сборке нет.

Каждый видит свою руку, ходы доезжают, таймер и связь показаны над столом.

Веб проверен отдельно: браузерная сборка вошла в комнату десктопного хозяина и сыграла с ним партию до конца (версия партии 16, победа набором F-I-R-S-T). По дороге выяснились две вещи, стоившие времени:

- **Чёрный экран в автоматической проверке — артефакт метода.** Игровой цикл висит на `requestAnimationFrame`, а его браузер в скрытой вкладке не вызывает вообще: замер показал ноль кадров за две секунды при `visibilityState: "hidden"`. Веб проверяется только в видимом окне.
- **Настоящий баг, который виден только в вебе:** клиент слал заголовок `apikey` во все запросы, включая свой API, и браузер отбивал их preflight-проверкой — сервер не перечислял этот заголовок в `Access-Control-Allow-Headers`. Теперь ключ уходит только на адреса Supabase, а сервер такой заголовок разрешает. На десктопе CORS не проверяется, поэтому там баг не проявлялся.

Ответы `409 stale_version` в консоли браузера — штатная гонка, а не ошибка: ход отправлен по версии, которую сервер уже обогнал ходом соперника; клиент запрашивает свежий вид и продолжает.

Ввод текста (ник, название комнаты, пароль, код) идёт системным полем `Gdx.input.getTextInput`: своей клавиатуры в игре нет. На десктопе это отдельное окно; в браузере — запрос браузера, и его поведение тоже ещё не проверено.

## 16. Открытые вопросы

1. Длительность хода: 60 секунд — предположение. Уточнить после первых живых партий; возможно, выбор при создании комнаты (30/60/120).
2. Считать ли партию за поражение при выходе из приложения — сейчас да, через таймер. Возможно, разумнее короткое окно на возврат.
3. Домен API: отдельный проект Vercel или те же функции рядом со статикой игры (сейчас она едет на `first-game.com/v2/` через GitHub Actions — см. [08-build-deploy.md](08-build-deploy.md)).
