# Сервер мультиплеера

Бэкенд сетевых партий: база и права доступа в Supabase, API на Vercel. Правила
игры сюда не переписываются — сервер зовёт ту же библиотеку, что и клиент,
собранную из модуля `gdx/rules` в JS.

Спецификация целиком: [docs/gdx/11-multiplayer-spec.md](../docs/gdx/11-multiplayer-spec.md).

## Что уже работает

| Часть | Состояние |
|---|---|
| Проект Supabase `first-game` (eu-central-1) | Поднят |
| Схема: `profiles`, `rooms`, `matches`, `match_views` | Применена миграциями |
| RLS: игрок видит только свой вид партии | Проверено `checks/rls-smoke.mjs` |
| Realtime на `match_views` | Проверено `checks/realtime-smoke.mjs` |
| Анонимный вход | Включён |
| API на Vercel | Развёрнут: `https://first-game-api.vercel.app` |
| Клиент игры | Этап M9.5, не начат |

## Настройка

```bash
cp server/.env.example server/.env    # заполнить своими ключами
set -a && . server/.env && set +a     # подхватить их в оболочку
```

Ключи берутся в Supabase → Project Settings → API Keys. Секретный ключ обходит
RLS: он живёт только здесь и в переменных окружения Vercel, в клиент игры не
попадает никогда.

## Устройство

```
api/index.js      единственная функция: свой роутер на все маршруты
lib/http.js       разбор запроса, коды ошибок, CORS
lib/auth.js       кто пришёл: проверка токена и профиль
lib/db.js         доступ к базе секретным ключом
lib/rooms.js      список, создание, вход, выход
lib/matches.js    старт партии, ход, сдача, тайм-аут, реконнект
lib/rules/        собранные правила из gdx/rules — не править руками
supabase/migrations/  схема и функции базы
checks/           проверки: права, Realtime, API целиком
```

Все маршруты обслуживает **одна** функция: на бесплатном тарифе Vercel их
двенадцать на проект, а эндпоинтов у нас больше. `vercel.json` переписывает
`/api/*` на неё, а разбор пути — в `lib/http.js`.

### Где всё стоит

Функция живёт во Франкфурте (`"regions": ["fra1"]` в `vercel.json`) — там же,
где база: проект Supabase в `eu-central-1`. По умолчанию Vercel ставит функцию
в Вирджинию, и каждое обращение к базе улетало через Атлантику. Ход делает
несколько запросов подряд, так что на ровном месте набегала секунда: измеренная
медиана хода была 920 мс при 260 мс на запрос без базы вовсе.

Отсюда же правило для этого API: **обращений к базе на запрос должно быть как
можно меньше**, а независимые — через `Promise.all`. Перелёт стоит дороже самой
выборки, даже когда они в одном городе.

### Маршруты

| Метод | Путь | Что делает |
|---|---|---|
| POST | `/api/profile` | завести или сменить ник |
| GET | `/api/rooms` | список открытых комнат |
| POST | `/api/rooms` | создать комнату (`name`, необязательный `password`) |
| GET | `/api/rooms/{id}` | состояние своей комнаты: пришёл ли гость |
| POST | `/api/rooms/join` | войти по `roomId` или `code`; партия начинается сразу |
| POST | `/api/rooms/{id}/leave` | выйти из лобби |
| GET | `/api/matches/current` | активная партия — возврат после обрыва |
| POST | `/api/matches/{id}/command` | ход: `version`, `kind` (`play`/`choose`), `index` |
| POST | `/api/matches/{id}/surrender` | сдаться |
| POST | `/api/matches/{id}/claim-timeout` | засчитать просрочку соперника |
| GET | `/api/cron/reap` | уборка по расписанию, под `CRON_SECRET` |

Ошибки приходят как `{"error": "код"}`; клиент разбирает код, а не текст.

## Правила игры в серверной сборке

```bash
./server/scripts/sync-rules.sh
```

Скрипт пересобирает `gdx/rules` в JS и кладёт результат в `lib/rules/`.
Эти файлы **коммитятся**: Vercel деплоит содержимое репозитория, а JVM и Gradle
там нет — собрать при деплое нечем. После любой правки правил скрипт надо
прогнать, иначе сервер будет считать партии по старым.

## Миграции

```bash
cd server
supabase link --project-ref "$SUPABASE_PROJECT_REF" --password "$SUPABASE_DB_PASS"
supabase db push --db-url "postgresql://postgres.$SUPABASE_PROJECT_REF:$SUPABASE_DB_PASS@aws-0-eu-central-1.pooler.supabase.com:5432/postgres"
```

Строка подключения именно через пул, а не через `db.<ref>.supabase.co`: прямое
подключение у новых проектов Supabase работает только по IPv6, и `db push` без
неё падает с `tls error (EOF)`.

## Деплой

```bash
cd server
vercel deploy --prod --token "$VERCEL_TOKEN"
```

Переменные окружения проекта (`SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`,
`SUPABASE_SECRET_KEY`, `CRON_SECRET`) задаются в настройках Vercel и в
репозитории не хранятся.

## Проверки

Все три создают свои данные и убирают их за собой, так что их можно гонять по
живому проекту.

```bash
./server/scripts/sync-rules.sh          # собрать правила перед проверками
node server/checks/rls-smoke.mjs        # права: свой вид виден, чужой нет
node server/checks/realtime-smoke.mjs   # ход доезжает по сокету
node server/checks/api-smoke.mjs        # партия целиком через HTTP
```

`api-smoke.mjs` по умолчанию поднимает функцию локально, без Vercel. Чтобы
проверить развёрнутый сервер:

```bash
API_BASE=https://first-game-api.vercel.app node server/checks/api-smoke.mjs
```

`realtime-smoke.mjs` заодно рабочий прототип протокола: Supabase Realtime
говорит кадрами Phoenix, и на этапе M9.5 такой же обмен пишется руками на Kotlin —
библиотеки Supabase в TeaVM не живут.

## Как устроен доступ к данным

- Клиент **не пишет** в базу вообще. Все изменения делает эта функция секретным
  ключом.
- Клиент читает ровно одну таблицу — `match_views`, и только свою строку в ней:
  политика RLS сравнивает `player_id` с `auth.uid()`.
- В `match_views` лежит уже отредактированное состояние: рука соперника и обе
  колоды заменены заглушками ещё до записи в базу.
- Полное состояние партии живёт в `matches`, куда клиенту хода нет ни на чтение,
  ни на запись. В `rooms` лежит хеш пароля комнаты, поэтому и список комнат
  собирает функция, а не прямой запрос: RLS умеет скрывать строки, но не столбцы.
- Вход в комнату и тайм-аут делают функции базы (`join_room`, `expire_matches`):
  это гонки по определению, и двумя запросами их не закрыть.
